# KBDI Rust prototypes, stage 2: how far below xclim

Working notes from 2026-10-15. Follows `../rust_prototypes/NOTES.md` (stage 1). Not
production code. Every number here is from this Windows ARM64 laptop (Snapdragon X Elite
X1E78100, 12 cores), from runs on a machine that was not idle; treat them as directional.
Quote nothing publicly until the suite has been rerun on the Linux runners
(`bench/kbdi-ci`) and on an idle machine.

## Contract

Every non-`ref_` variant is checked against `climate_core::fire::kbdi` before timing and
must stay within the native-parity tolerance `rtol = atol = 1e-10`. Observed: max abs
diff ≤ 3.3e-13 mm on all four benchmark workloads and on synthetic stress inputs
(cold climate, 40 % rain days, MAP 50–4000 mm, `T = ±1e4`, 70 °C). The `ref_cm` and
`ref_dm` variants are the stage-1 bit-identical loops, kept as baselines.

None of this is bit-identical to the shipped kernel. The upside: the shipped kernel's
bits already depend on the platform C runtime's `exp` (Windows CRT, glibc and macOS
differ), while `heat_texp` uses no library call and no FMA, so these kernels give the
same bits on every platform.

Every kernel assumes complete input (all values finite). A production version scans the
input once and falls back to the existing driver on any non-finite value, seasonal mask,
spin-up or carried state it does not handle.

## Where the time went (measured, grid_400, 1 thread)

| piece | time | note |
|---|---|---|
| shipped kernel | 28.8 ms | |
| stage-1 best bit-identical (`ref_dm`) | 8.4 ms | |
| fraction pass alone, polynomial `vexp` | 4.15 ms | latency-bound: about 60-cycle chain |
| fraction pass alone, table `heat_texp` | 2.03 ms | |
| 8-lane recurrence alone (no `exp`) | 1.05 ms | 0.72 ns/cell-day |
| committing a fresh 11.7 MB output (Windows) | 1.3–2.4 ms | measured with `KBDI_REUSE=1` |

Single station: the bit-identical step is a serial chain
(`sub max sub mul div mul max add min`, about 30 cycles). That chain is the whole
station runtime.

## The ideas, in order of payoff

1. **Short chain** (`cm_scalar`). Move everything that does not depend on the index off
   the chain: `k = max(heat * (1e-3/den), 0)` (0 below 10 °C), then
   `Q = min(203.2, Q1 + (203.2 - Q1) k)`. Branch-free wet-spell selects. Station:
   100.8 → 55.6 µs on its own.
2. **Table-driven `exp`** (`heat_texp`). A 256-entry `2^(j/256)` table (generated by
   `gen_exp_table.py`, correctly rounded) and a degree-4 polynomial on |r| ≤ ln2/512.
   `0.968` is folded into the argument as `+ ln 0.968`. There is no lower clamp, because
   the `T ≥ 10` select discards those lanes. No `round()`, no float-to-int conversion and
   no `mul_add`: those are libm calls on the x86-64 SSE2 baseline that wheels target.
   - It is half the cost of the best branch-free polynomial (`vexp`, a degree-11
     economized Estrin form, kept for comparison).
   - A Horner degree-12 polynomial was worse again: about 15 cycles per element,
     latency-bound.
3. **Independent cells in lanes** (`cm_lanes<8>` for `[cell][day]`,
   `dm_tiled<8, 256, 32>` for `[day][cell]`). Each lane's chain is hidden behind the
   others, and the fraction vectorizes across lanes.
   - Day-major needs tiling: untiled 8-column lanes walk rows 20 KB apart and thrash the
     TLB (grid_2500 64.7 ms → 36.8 ms tiled).
   - `L = 8` is best; `L = 16` spills registers.
4. **Time-parallel scan for one series** (`cm_scanf8`). The daily map
   `Q ↦ clamp((1-k)Q + 203.2k − (1-k)·net, 203.2k, 203.2)` is monotone clamp-affine, and
   such maps compose in closed form. The series is split into 8 chunks, each starting
   right after a dry day (empty wet spell). The maps are composed in lanes while
   computing the fractions (pass 1), the 8 start values are chained (pass 2), and the
   chunks are rerun in lanes (pass 3). Error stays at 1e-13 because every chunk reruns
   the real step from a start value good to an ulp. If a series is too short or has no
   dry day to split at, it falls back to the plain loop.
5. **Output allocation.** Committing fresh pages costs about 45 % of a single-threaded
   grid run on Windows and caps 12-thread runs. xclim pays the same.
   - `mimalloc` as the global allocator (feature `mimalloc`, separate target dir)
     reuses freed blocks across calls. It cut grid_2500 from 33.5 to 20.6 ms
     single-threaded.
   - This is a steady-state result for repeated calls in one process (dask chunks,
     loops), not a first-call result. It is reported separately below.
6. **Threads.** Give each worker its own block and output (`_mtb`). Writing one shared
   allocation from 12 threads is slower: page-fault contention, plus tiles sharing rows
   for day-major. Use a persistent pool (`_mtp`, Rayon): spawning 12 scoped threads
   costs 0.3–0.7 ms per call.

## Results, same session, back to back (`../out/fast_compare.jsonl`, `../out/fast_timings.jsonl`)

System allocator, as the protocol requires (fresh output every call):

| workload | xclim | shipped | best bit-identical | **best here** | × xclim |
|---|---|---|---|---|---|
| station_1825 | 19.9 µs | 31.3 µs | 16.7 µs | **6.1 µs** `cm_scanf8` | 3.3 |
| station_10958 | 114.2 µs | 190.2 µs | 100.8 µs | **36.0 µs** `cm_scanf8` | 3.2 |
| grid_400, 1 thread | 17.3 ms | 28.8 ms | 8.4 ms | **4.3 ms** `dm_tiled_256x32` | 4.0 |
| grid_2500, 1 thread | 108.4 ms | 164.7 ms | 52.6 ms | **33.5 ms** `cm_lanes8` | 3.2 |
| grid_400, 12 threads | 1.81 ms¹ | — | — | **1.20 ms** `dm_tiled_256x32_mtp` | 1.5 |
| grid_2500, 12 threads | 11.4 ms¹ | — | — | **7.2 ms** `dm_tiled_256x32_mtp` | 1.6 |

¹ xclim `kernel_threads`: its gufunc on 12 row blocks from a persistent
`ThreadPoolExecutor`, each block allocating its own output.

With `mimalloc`, steady state for repeated calls:

| workload | **best** | × xclim |
|---|---|---|
| grid_2500, 1 thread | **20.6 ms** `cm_lanes8` | 5.3 |
| grid_400, 12 threads | **0.75 ms** `cm_lanes8_mtp` | 2.4 |
| grid_2500, 12 threads | **4.9 ms** `cm_lanes8_mtp` | 2.3 |

At 12 threads with reused memory, grid_2500 moves about 219 MB in 4.3 ms
(51 GB/s), so it is near this laptop's memory bandwidth.

## Variants (`src/main.rs`, `src/kernels.rs`)

| variant | layout | what |
|---|---|---|
| `production`, `ref_cm`, `ref_dm` | | shipped kernel; stage-1 bit-identical loops |
| `cm_scalar` | cell | short chain, CRT `exp` on warm days |
| `cm_block_vexp`, `cm_block_texp` | cell | per 512-day block: fractions, then recurrence |
| `cm_lanes{2,4,8,16}`, `cm_lanes8_vexp` | cell | cells in lanes |
| `cm_scan{4,8,16,32}`, `cm_scan8_vexp` | cell | time scan, separate fraction pass |
| `cm_scanf{4,8,16}` | cell | time scan, fractions fused into pass 1 |
| `cm_auto` | cell | scan for fewer than 8 cells, lanes otherwise |
| `dm_simd`, `dm_simd_vexp` | day | whole row per day, state in arrays |
| `dm_lanes{4,8,16}` | day | 8 adjacent columns in lanes, untiled |
| `dm_tiled_{W}x{B}` | day | lanes in W-column tiles, B days at a time |
| suffix `_mt` / `_mtb` / `_mtp` | | shared output / own block per scoped thread / own block on a Rayon pool |
| `probe_fraction*`, `probe_lanes8`, `probe_spawn` | | throughput probes, not KBDI (check skipped) |

`KBDI_REUSE=1` recycles the output buffer between calls (diagnostic only, not
protocol-fair). The `allocator` and `reuse_output` fields in each JSON line record how it
was run.

## Run

```bash
cd benchmarks/kbdi_competitors/rust_fast && cargo build --release
cargo build --release --features mimalloc --target-dir target/mi   # allocator experiment
cd .. && rust_fast/sweep.sh "station_10958 grid_400x3650" "cm_scanf8 cm_lanes8 dm_tiled_256x32"
rust_fast/sweep.sh grid_2500x3650 "cm_lanes8_mtp dm_tiled_256x32_mtp" 12
```

On Windows ARM64, mimalloc's MSVC build references the x86-only `__popcnt64`; `main.rs`
supplies it under the feature.

## Open questions and next steps

1. **Linux runners first.** Mirror `rust_fast/` into `bench/kbdi-ci` and rerun. Two
   things to check:
   - the x86-64 SSE2 codegen of `heat_texp` (2 lanes, no FMA);
   - whether numpy's `madvise(MADV_HUGEPAGE)` on large arrays explains the stage-1 Linux
     gap: xclim's output gets huge pages and our `Vec` does not. If it does, allocate the
     output through numpy (or `madvise` it) in `climate-py`.
2. **x86 AVX2 dispatch.** Use `#[target_feature(enable = "avx2")]` plus
   `is_x86_feature_detected!`. It gives 4 lanes with the same bits, as long as FMA stays
   off.
3. **Production shape.**
   - A fast path in `fire::kbdi` for complete input, no season mask and no spin-up:
     `dm_tiled` for `[day][cell]`, `cm_scanf8` when there are fewer than 8 cells.
   - The driver keeps everything else.
   - Changing the shipped bits needs a changelog note; parity tests stay at `1e-10`.
4. **Layout.** The xarray path copies time-last blocks into time-first ones
   (`_kbdi.py`, `np.moveaxis(...).copy()`). A kernel that takes either layout removes
   that copy.
5. **Other recurrences.** The same three levers (short chain, table `exp`, lanes) likely
   apply to DMC and DC; the time scan applies only where the daily map is monotone
   piecewise-affine. Not measured here, as agreed.
6. **Allocator.** Whether `climate-py` should ship mimalloc (or keep a buffer cache) is a
   product decision. It only pays for repeated calls.
